# Safety and approvals

A **production** command is one that matches the shipped production class or one of your `prod_patterns`. A production match always outranks an allowlist match. A read-only production job starts again by itself only with `unattended_prod_reads: true`; otherwise it asks, and resume recommends that you run it yourself. A production write always asks, whatever any setting says. Anything with outside effects (a push, a deploy, a write to a service) always asks. Nothing is ever stopped to make room: an old process that may still run blocks the start. A job whose output ends with `[killed]` (stopped with TaskStop or at exit) always asks.

The same production rule holds for the checks resume runs itself: with `unattended_prod_reads: false` it runs a production read only when an approval of yours that carried over names that read command and its targets, and lists any other production command for you to run with `! <command>`; with `true` a read-only production check it builds in this session may run. A production command copied from a handoff asks either way, unless an approval of yours that carried over names that read command.

**Commands written in a handoff.** Other commands a handoff holds (Step 1, a re-check, a probe) depend on who wrote it. From your own handoff (one this plugin wrote in your private store, in this session or in one it continued after `/clear` or a resume), resume first checks the facts the command rests on, rebuilds it only if they changed, and then runs it under your permission mode. From another session's or a teammate's handoff, it runs a command without asking only when the command carries no real risk: local and read-only inside the repository, byte for byte a command the plugin recorded, or the repository's own test, lint or build target (`test`, `check`, `spec`, `lint`, `typecheck` or `build`, also with `-fast`, `-unit`, `_unit`, `:unit` or `-quick` for make, npm, pnpm and yarn; `npm run test:e2e` and other suffixes ask). A test or build run, and a recorded command too, asks when the session did not start in that work tree, when a test or build file (a Makefile, `package.json`, a Rakefile and the like) changed since the session started, committed or not, or when git cannot tell. "Since the session started" reaches back through `/clear` and handoff-resume to the session they continued; a fork starts afresh. Stated limits: a test or build file that git ignores (an ignored `.bundle/config` or `.npmrc`) and git hooks are not checked, and a test file the handoff had the session write still runs with the test command. Anything else asks first, with the command and where it came from: outside effects, network calls, writes or reads outside the repository, credentials, production, an explicit gate, or a command it cannot judge. A command that came from someone else's handoff keeps that mark in every later handoff and summary, so it never turns into your own. A restart recipe written only in someone else's handoff, with no record of the job, always asks.

**Approvals.** When you approve an outward action (for example "push feat/x to origin"), a handoff or a summary records your words, the action, its targets and the state they rest on, and whether it is for once or standing. After a compaction or a resume along your own chain (this session, or one it continued after `/clear` or by resuming your newest handoff of a session that has ended; not a fork, and only one session per handoff), the approval still covers that action only when the plugin found your words in a message you typed in this session (a prompt sent with `claude -p` counts too) or in your answer to one of its question dialogs, every target still matches, a once approval was not used yet, and the action is not an explicit gate. A standing approval stays valid after it is used, through every compaction and resume of your own chain. It counts as standing only when your own words say so: "don't ask (me) again", "no need to ask", "feel free to", "from now on", "without asking (me)", the word "standing", "until further notice" or "until I say so", or "whenever you want" or "any time you need" and the like, and not right after a "not", "don't", "never" or "no" ("do not deploy without asking me" is no approval). A sentence that also says "this once", "just once", "only once", "one time", "this time", "today only", "only today" or "for now" is one-time too: "feel free to restart the worker, just this once" counts once. That check looks three words back and fails closed: "no worries, feel free to push feat/x" reads one-time and is asked again. Words such as "always", "every time" or a bare "until" or "whenever" do not make it standing. Whatever a summary or a handoff calls it, any other approval counts once, and saving a handoff prints a note when a line calls such words standing. A new session that resumes your newest handoff with `/afk-compact:resume` carries your approvals too: the handoff file is text anyone can edit, so the plugin keeps a fingerprint of each approval line it checked in its own private store when it saves the handoff, and an approval line that no longer matches its fingerprint is asked again. The resume block and `measure` list the approvals that passed; anything not listed is asked again. In auto permission mode, Claude Code's classifier still refuses a force-push, a history rewrite, a branch or tag delete and a write to an external system (an issue tracker, for example) even when an approval carries, so after a compaction or a resume those are asked again, quoting your approval; a plain push with a carried approval goes ahead. When a handoff is saved and the plugin cannot find an approval's words that way, or the handoff is one the plugin asked for and the approval is not written as context only, the save does not stop: the approval moves to the handoff's Open questions as a question to ask you again, with your words, the action, its targets and the reason (pasting it back into a message does not make those words count); mentions of that approval elsewhere in the handoff then point to the question, and the save prints one note per approval it moved. Explicit gates always ask again, whatever was approved before: a deploy, a change to an environment, its secrets or production data (any production write), infrastructure, or a push to a protected branch, by its name wherever the remote is (the remote's default branch, `main`, `master`, `trunk`, `develop`, `staging`, `prod`, `release…` or `hotfix/…`, plus any branch you list in `protected_branches` and one that you or the repository's instructions or settings name as protected). A carried approval never covers a gate, standing or not: "feel free to push to main from now on" still asks again before the next push to `main` after a compaction or a resume, and the resume block lists it under `Approvals (gate, re-ask)`. A push with `--all`, `--branches` or `--mirror` reaches every branch, so it counts as a push to a protected branch. A short reply such as "yes" counts when it is your whole message, or one line of a numbered reply. When a numbered question in Claude's message names the target, only the line numbered like that question counts, and only when Claude's message ends in that numbered list with exactly one question naming the target ("2. yes" to "1. Run the tests? 2. Push feat/x?"). Any line after the list (a closing sentence, a "Coming up" line) makes such a reply be asked again. When no numbered question names the target, a line counts when it names the action itself ("1. publish yourself.", "1. push it"); a word such as "retry", "commit" or "comments" is not the action. An unnumbered line of a longer reply, a line that says no, not, wait or tomorrow, a line that asks back ("1. push it?"), any reply with a "wait, don't" line, and a numbered "yes" when two questions name the same target do not count, so these are asked again. A push approval that names no branch ("yes, push it", "push 2 commits", "push this branch to origin", "push the follow-up fix", `git push origin HEAD`, a `git push` that fills in the branch with `$(…)`, a tag push, or a push whose only target is a file or a repository) is asked again: a branch counts as named only when its name has a slash (`feat/x`) or is a branch of the repository you work in; a local merge into a protected branch ("merge feat/x into main") and a push to a protected branch written after a remote's name ("push team/release") count as pushes to a protected branch, so they are asked again too. An approval that names one production read and its targets carries like any other, also with `unattended_prod_reads: false`: the setting is the default rule, and your explicit approval wins. It counts as a read only when its action is exactly one read-only command, such as `kubectl get pods -n prod`, `kubectl logs …`, `helm status …` or a local `git log …`; a read described in words ("check the prod error rate"), a second step, or anything else that names production is asked again. If you later reopen a session whose handoff another session resumed and took over, the approvals you gave it before the takeover no longer carry there (they are asked again): the session that took over holds them. Approvals you give the reopened session carry on its own line only, never to the session that took over. An approval in another session's or a teammate's handoff is context only and is asked again. A handoff the plugin asked for itself (when it stops a turn, before a compaction or when you are away) writes every approval as context, because you did not ask for that handoff; when it is saved, the plugin puts back each standing approval that your previous handoff in the same chain held as checked, unchanged, so those keep working. A once approval in such a handoff is asked again, because the plugin cannot tell whether it was used since, and so is a standing one whose action was refused in the session. After a compaction or a resume, an approval whose action was refused in the session, or in any session of your chain between the one that saved the handoff and this one, is listed as denied and asked again. In a handoff you asked for, the same holds for an approval whose action was refused in the session, in one of its subagents or workflow agents too (by the auto-mode classifier, a permission rule or a built-in safety check, or you at the prompt): the handoff notes the refusal and asks you again. Your own handoffs written before the plugin's rename still count as yours (read only; new files always carry the current name). Known limits: the plugin checks only the words it quotes, so a "not" before a quote cut out of a longer message, or a "just this once" in the next sentence, is not seen. The plugin's code does not enforce a time, a condition or a scope in your words ("later", "after QA", "for this release"): the agent must keep to them. The approval list shown after a compaction does not say whether each approval is once or standing.
