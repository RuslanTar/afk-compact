# Near a usage limit <!-- Source of docs/usage-limits.md and part of plugin/README.md. Compare only with Claude Code's own behaviour, never name another plugin or tool. Plugin idle compaction and keep-warm read each usage limit Claude Code reports on its own: the five-hour window (Claude Code's session limit), the seven-day window and a gateway's spend limit. There is no setting for this; the rule adapts to what the plugin measures:

- Below 90% no limit stops them.
- A spend limit (a money cap) stops them at 90%.
- The five-hour or seven-day window stops them at 90% too, unless all of these hold; then they go on up to 98% of the five-hour window or 95% of the seven-day one (going past the seven-day limit stops every session of your account for days):
  - an agent, a workflow or a working teammate of the session is still open, so its result will open a turn that reads the whole conversation again, which costs more read cold than a compaction does (a background shell alone does not count: it may never end);
  - the reading is from the last 10 minutes: going past 90% needs a current share, so an older one stops them at 90% (rule `stale`);
  - the share plus the largest change of the last five plugin compactions in that window (at least one point), plus one point, stays below that cap. The plugin measures that change itself, from the share right before and right after each of its compactions, so a small plan, where a compaction moves the share by several points, gets less room than a large one; until a change is measured, 90% stands.
- In that band keep-warm sends no more requests: it hands the idle gap over once to plugin idle compaction while the cache is warm.
- When every window that stops keep-warm (or holds it in that band) resets before the next request would come too late for the cache (58 minutes after the last one), keep-warm waits and sends that request just after the reset instead.
- A share whose reset time has passed counts for nothing.

**Which readings count.** Skipping near a limit is the costly mistake: the session goes cold, and its next turn writes the whole conversation to the cache again, while running when it was not needed costs one request or one compaction. So the plugin skips only on readings it can trust:

- It reads every reading it has of each limit: the session's own, its status line's (with `--note-usage`, see [the status line](status-line.md#the-cache-state-in-your-status-line)), and those of your other sessions on this machine, which the plugin keeps in one small file until each one's limit resets.
- A reading counts until its limit resets, however old it is. Until the reset a limit's share only grows, so a reading of 99% from an hour ago still means the limit is near; and nothing refreshes a session's reading while it sits idle (keep-warm's requests do not). A reading whose reset time has passed counts for nothing, and one with no reset time counts only while it is from the last 10 minutes.
- Readings of a limit with the same reset time (within a minute) are of one period, and the latest of them is that period's share. A reading whose time is not known (one dated more than a minute ahead of the clock, or the session's own just after a plugin reload, before Claude Code refreshes it) is the latest only when its share is the larger, since the share only grows. A status line gets the session's reading without its time and shows it again while it is on screen, so a status line's reading never counts as newer than the reading the plugin itself has of that session.
- A limit stops them only when every period of it that the readings show is at or over the limit. If one has room, they run: behind a proxy that spreads requests over several accounts, each account has its own period (its own reset time), and the next request may go to the one with room.
- With no reading that counts, they run.
- A period whose reset time is more than an hour from the others' still counts; the log marks it (`usage_anomaly`). Behind such a proxy each response can come from another account, and a compaction can move a session to another one, so its reading jumps.

The idle handoff turn keeps its own setting, `idle_handoff_near_limit`, and reads the readings the same way. When no limit is reported (a session restarted in the idle gap reports none before its first response), the session's own readings in that file stand for it, with the other sessions' beside them; after a plugin reload they are read beside the reported one too. With none there (an API key), keep-warm skips this check; plugin idle compaction and the idle handoff turn then have only the share read when the last turn ended, which counts only while it is from the last 10 minutes (it never is by the time they run). Each skip or stop for a limit logs the rule that decided in `rule` (`band`, `cap`, `no-job`, `stale`, `no-delta`, `delta`, `spend-90`, `other-90` or `arm-90`; the idle handoff turn's skips under `idle_handoff_near_limit`: `option-skip` or `option-skip-spend`), a plugin idle compaction, keep-warm request or idle handoff turn that ran with a reading at the limit says why (`split`: another period had room; `no-fresh`: no reading that counts, only ones with no reset time older than 10 minutes), and, when Claude Code's environment has them, `CLAUDE_CODE_SUBSCRIPTION_TYPE` and `CLAUDE_CODE_RATE_LIMIT_TIER` as `plan` and `tier`; each plugin compaction logs the plan windows' shares before and after it (`pct_before`, `pct_after`). These rows also say where each window's reading came from, `plugin` (the session's own), `statusline` (its status line's `--note-usage`) or `peer` (another session on this machine), how old it was in seconds and how many periods of it counted (`usage_src`, `usage_age_s`, `usage_n`; on a compaction `usage_age_s_before` and `usage_age_s_after`). `/{{plugin}}:status` shows the session's last reading of each window with its source, age and reset time (marked when it does not count), and the readings of your other sessions on this machine that count.
