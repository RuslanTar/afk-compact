With `queue_cmd` set, the checkpoint nudge asks the model to queue each question that waits on you, using the plugin's `queue-add` helper command in the nudge's listing batch. The helper scans the draft for secrets (a hard hit sends nothing, a soft hit is redacted) and runs `queue_cmd add --json --session <sid> --client-id <id>` with the draft on stdin. It always uses your own session's lane, never picks a lane for you, and never calls `adopt`.

The client id comes from the question, so the same question is not queued twice; the helper keeps `queue-adds.jsonl` for that. If the add fails for any reason (unsupported, lane held, no lane, invalid draft, error, timeout), the helper prints `NOT QUEUED` and the question stays in the handoff as before. A queued question is a question, never an approval. Only `/{{plugin}}:resume` calls `adopt`.

**Off, on and degraded.** With `queue_cmd` empty the queue is off: the plugin makes no queue call, and `/{{plugin}}:status` says `queue: off`. With it set, the queue is on (`queue: on`) only while your program keeps the contract below. If the path is not an executable file, or a `list` reply is not one JSON object with `"schema": "queue-stub/v1"`, the queue counts as degraded: the plugin uses nothing from the reply, the handoff gets no `Queued:` line, and `/{{plugin}}:status` names the reason (for example `queue: degraded (untagged)`). `queue_cmd` is read from your settings file only (see [Settings](configuration.md#settings)).

**The contract.** It ships with the plugin as `assets/queue-contract.md` in the plugin folder (`plugin/assets/` in the source repository), with a JSON Schema for each JSON document: `queue-stub.v1.schema.json` for the `list` reply and `queue-add.v1.schema.json` for the `add` draft. It lists the three subcommands with their arguments, every key and size cap of the two documents (for example `recommendation_none_reason`, at most 200 bytes), the exit codes and what the helper prints for each, and how long the plugin waits (5 seconds at most; 3 after a compaction).

## Connect your own question queue

**What the plugin sends, and when.** The plugin runs your program with a subcommand and flags only; it never passes a root folder or a project, so the program keeps its store where it chooses.

- `list --json --session <session id>`: at each checkpoint, at the start of a handoff, after a compaction, when `measure --compact` runs and in the local comparison trial (which waits 1.5 seconds). The program answers with the session's lane and its open questions; the handoff then says how many are open, and the model is told they are answered only via the queue.
- `add --json --session <session id> --client-id <id> [--lane-name <slug>]`, the question as a JSON draft on stdin: at a checkpoint, once per question that waits on you, after the secret scan; not while the last `list` reply from the program file as it is now (path, modification time and size) had no `commands` or left `add` out, nor for a day after an `add` exited 2.
- `adopt --lane <id> --if-free`: only from `/{{plugin}}:resume`, when a new session picks up a handoff whose lane is named (`lane:`); once more without `--if-free` when another session holds the lane and you say to take it over, and with `--must-exist` when the program lists `adopt:must-exist`.

**A minimal program.** `assets/examples/queue-folder.sh` (about 40 lines of POSIX `sh`) keeps each queued question as one JSON file, `<folder>/<session id>/<client id>.json`, with the folder from `QUEUE_DIR` (default `~/.local/state/my-questions`). It answers `list` and `add` and leaves `adopt` out, which the contract allows. Copy it somewhere of your own (the plugin folder is replaced at each update) and keep it executable: `cp "<plugin folder>/assets/examples/queue-folder.sh" ~/bin/my-queue && chmod 755 ~/bin/my-queue`.

**Setting `queue_cmd`.** It names a program the plugin runs, so it is a consent key: set it yourself, in `/config` (the plugin's "Question queue program" row) or by typing `! printf '%s' '{"queue_cmd":"~/bin/my-queue"}' | claude plugin configure {{plugin}}@<marketplace> --values-stdin` with your program's path (a full path, or one that starts with `~/`). The plugin's settings commands never change it; they print that line for you to type. Empty it the same way to turn the queue off.

**Testing.** `! "<plugin folder>/scripts/{{plugin}}-store" queue check` (or `queue check <program>` for a program not set yet) runs your program's `list` once with a made-up session id and prints one `ok` or `FAIL` line per check, each failure with its fix: the file is executable, `list` exits 0 within 1.5 seconds, prints one JSON object tagged `queue-stub/v1`, and every key has the type and form the contract gives. It ends `QUEUE CHECK PASS` (exit 0) or `QUEUE CHECK FAIL <check>` (exit 1). It writes nothing and never calls `add` or `adopt`, since those write and the contract has no dry run; the contract's Testing part shows an `add` call to try against a scratch folder (`QUEUE_DIR=/tmp/q-test` for the example). While `queue_cmd` is set, `/{{plugin}}:status` lists `queue check` under the user-run commands. After a checkpoint, `/{{plugin}}:status` still says `queue: on`, or the reason the plugin stopped reading the replies.
