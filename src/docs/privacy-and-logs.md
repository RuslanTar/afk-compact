## Privacy

- **Local only.** No telemetry, and the plugin opens no network connection of its own. The extra model requests it asks for (handoff turns, keep-warm, its own compactions) go through Claude Code like any turn. A report is a zip on your disk; whether you send it is up to you (see [Sending a report](#sending-a-report)). The comparison trial, off by default, makes its model calls through Claude Code (see [A local comparison trial](#a-local-comparison-trial-off-by-default)).
- **Content-free logs.** Log rows never store summary or handoff text, your or the model's messages, commands, file contents, permission-denial reasons, environment values or secrets. An unknown value is logged as the class `other`. The one file with command text is the job record (`jobs.jsonl`), which the plugin needs to start a lost job again byte for byte. A command with a hard secret hit is stored as a hash and rule ids only; a command with only a weaker hit (such as `password=…`) is stored as typed and can appear in a published restart recipe. See [Lost background jobs](background-jobs.md#lost-background-jobs).
- **In-process reading.** Summaries, transcript rows and commands are read in memory to compute classes and counts, then dropped.
- **Secrets.** Summary copies with a hard secret hit are saved redacted. Evidence files that look like credentials (`.env`, keys, `.netrc` and similar) are withheld; logs and JSON with a hit are copied redacted; other files with a hard hit are withheld. Only rule ids are logged, never values. `/{{plugin}}:handoff` scans its draft before publishing: a hard hit blocks it, and a warning names the rule ids and the draft's line numbers, never the value.
- **Private files.** `umask 077`; the private store is never inside a git work tree (unless the path is git-ignored) or a `.planning/` folder. In repo mode the only write into a repository is the scanned export, and the plugin never stages, commits or pushes it.
- **No background actions.** Alerts never trigger an action. The plugin never stops background work. It never restarts or wakes it either: only `/{{plugin}}:resume` can start a lost read-only or allowlisted job again, after the checks above, and everything else asks you first.

## Watcher

With `watcher: true` (the default) the plugin keeps a local record of how compactions went. Nothing is sent anywhere. The first session after the install shows one notice:

```
{{plugin}}: local compaction logs are on (content-free; nothing is sent). To share them: /{{plugin}}:report. To turn them off: set watcher to false in /config.
```

It shows again only after an update that changes what is logged in a way you would care about. When the mod does not run (for example under a managed policy), the notice cannot show, and `/{{plugin}}:status` carries it instead, as a line `notice: ` followed by the same text, until a session has shown it.

The first line of `/{{plugin}}:status` is a verdict on this session: `ok: 5/5 compactions saved this session, no open alerts`, or `attention: 2 open alerts (A-01, A-05); 4/5 compactions saved this session` when an alert is open or a compaction has no saved copy. Open alerts are the warn and critical ones; an info alert is a note. Without a session id the verdict covers every session's last 7 days. The watcher's own line comes next: `watcher: true · logs <size> in <n> sessions · share: /{{plugin}}:report · off: watcher = false in /config`. <!-- 0.1.3 alert noise -->

Under `log_dir` (default `<handoff_root>/.watch/`):

| File | Holds |
|---|---|
| `<session>.jsonl` | Mod events: dispatches, compaction results, nudges, continues, halts, resume deliveries, settings in effect |
| `<session>.classic.jsonl` | Hook and helper events: shaped or fallback, copy results, verdicts, evidence counts, sweep counts, permission denials (tool name and class only), each Stop's timing |
| `<session>.alerts.jsonl` | Alerts raised for this session, and an `alert_closed` row for each one closed later |
| `<session>/compactions.jsonl` | One summary row per compaction. On the plugin's own path, the sizes Claude Code reported (tokens before and after, duration) come in a separate `compaction_boundary` row that readers join by the compaction's nonce; the copy's frontmatter keeps what was known when it was saved |
| `<session>/bg/slot-0.json` … `slot-19.json` | A fixed ring of 20 background-task snapshots (ids, kinds, status, output paths) |
| `<session>/dispatch/`, `checkpoint/`, `offsets/`, `paths.jsonl` and small marker files | Per-compaction records, git and project-state measurements, transcript read offsets, and the temp paths the session cited (a piece of a command, such as `/tmp/run-$n`, `/tmp/*.log` or `/tmp/out-%d`, is not recorded) |
| `<session>/resume-pending.json`, `resume-armed.json` | The facts a resume block still waiting for its turn is built from, so a resumed session gets it; rewritten without them once it is delivered, replaced or dropped |
| `<session>/pending/` | The raw summary text handed between hooks so the copy can be written, and kept mismatches (`*.mismatch.md`, redacted, with a `*.mismatch.json` of hashes) |
| `<session>/jobs.jsonl`, `jobs-pending.jsonl` | Background shells the mod recorded (time, folder, output file, and the command text unless it held a hard secret hit), and relaunches waiting for a matching job. See [Lost background jobs](background-jobs.md#lost-background-jobs) |
| `<session>/handoff-turn/` | One small record per handoff turn: its id, reason, budget, stage and published markers (see [The handoff turn](handoffs-and-resume.md#the-handoff-turn-of-a-last-cycle)) |
| `<session>/queue-adds.jsonl` | One row per question sent to `queue_cmd add`: client id, result, queue id. No question text |
| `<watch>/queue-caps.json` | Whether your `queue_cmd` supports `add`, cached for a day |
| `evidence-index.tsv`, `heal/` | Evidence dedupe index, restart counters of the resume skill |
| `version.json` | The mod's version record: the Claude Code version its last session start saw, the one before, and whether a smoke check is due after an update (`/{{plugin}}:status` shows it) |
| `.orphans/` | Empty markers for sessions that still have raw summary text under `pending/` |
| `notice/` | One marker per notice already shown |
| `export-salt`, `install-id` | Written the first time you make a report: a random salt for the hashed ids in reports, which never leaves your machine, and a random install id |
| `reports/` | Report zips, when `~/Downloads` is missing, not writable or inside a git work tree |

One file lives outside this folder: `last-version`, the classic hooks' version record. It holds the Claude Code version the last session start ran, for the version change row in the log, and works without the mod. It is kept in this plugin's own data folder, `<config>/plugins/data/<plugin>-<marketplace>` (`<plugin>-inline` for a `--plugin-dir` run), the name Claude Code gives that folder. When `CLAUDE_PLUGIN_DATA` names another plugin's folder (another plugin can set its own in session shells), the plugin still uses its own folder beside it, so there is one record and a version change is logged once. Another plugin's folder is never read or written.

Rows hold ids, counts, sizes, times, classes and rule ids. The files under `pending/` and the copies under `compact/` hold summary text, the files under `checkpoint/` hold the measured git file list and project-state lines, a waiting resume block (`resume-pending.json`, `resume-armed.json`) holds its measured lines, the saved copy's path, the text of an open question it quotes and the summary's Step 1 (at most 100 characters), and `jobs.jsonl` holds the command text of background shells; treat them like the summaries themselves.

Alerts are listed in `/{{plugin}}:status` with their seven-day counts. In this version they are not shown in the chat. The watcher raises no alert for what it could not observe.

- A compaction from before the session's first plugin row (a session that was already running at the install, or was resumed or forked after it) raises no missing-copy alert (A-01), no band alert (A-05) and no missing-hooks alert (A-15); the other checks still read it. When a session has only the rows its own Stops wrote, the first of those counts as its first plugin row, and when it has no row yet (the plugin was installed or reloaded mid-session and its first hook is a Stop), that Stop's start counts.
- A-05 also skips an idle compaction, which runs on the idle timer, not at a size; besides the plugin's own records, Claude Code's "Compacted while idle" notice right after a compaction marks it idle.
- The continue-without-nudge alert (A-27) skips a compaction from before the session's first plugin row and an idle compaction too, and never takes the plugin's handoff-turn message for a continue, also when that turn's record is gone.
- Without the plugin's mod (only its classic hooks), the band behind A-05 follows Claude Code's `autoCompactWindow` setting when `native_window_tokens` is unset, as the mod does, with the project's settings read from the project root. Claude Code never compacts past the model's own window, which the watcher cannot see, so a setting above 200,000 counts only once the session's context has been above 200,000; until then that band is off.
- The stalled-item alert (A-11) needs output the watcher can see. A background shell has a file even when its result did not name it: `<tmp>/claude-<uid>/<project>/<session>/tasks/<id>.output`, where `<tmp>` is `CLAUDE_CODE_TMPDIR`, else `/tmp`; for a subagent that file links to its transcript, and a background workflow writes its run journal and its agents' transcripts beside the session's transcript (`<session>/subagents/workflows/<run>/`), so A-11 checks those; a workflow counts as moving while any of them changes. A teammate or monitor has none the watcher can see, so A-11 skips them.
- The lost-rule alert (A-09) counts a ledger line as lost only when the new summary has neither its id (also when another ledger line carries it, see below) nor a line with the same text under another id (a renumbered line; case, spacing and a trailing check time do not count). Another ledger line carries an id only in the list of ids it starts with (`U-2, U-3: done`), also after a `;` or `·` that joins two entries; an id the text only cites (`per U-3`) carries nothing. <!-- 0.1.3 alert noise: A-01, A-15, A-05, A-11; 0.1.4: A-27, A-09, A-11 subagents and workflows, idle notice, autoCompactWindow, handoff-turn text, workflow agents -->

On its first Stop after an update, the watcher re-checks the open alerts that an older version wrote under a rule that changed since (A-01, A-05, A-11 and A-15 in 0.1.3; A-09 and A-27 in 0.1.4), in every session's log. It closes the ones the changed rules would not raise, by adding an `alert_closed` row with the reason `superseded: rule changed in <version>`; it deletes no row. A log is checked again when a process still running the older version adds to it. An A-11 alert stays open only when the item's output (a shell's output file; for a workflow, its run journal and its agents' transcripts) had not changed for the 15 minutes before the alert; when it changed after the alert, the watcher cannot tell whether the item was quiet then, so that alert is closed too. The verdict, the list of this session's alerts and the seven-day counts count only open alerts. For 7 days `status` also shows how many alerts were closed this way. <!-- 0.1.3 alert noise: superseded rows -->

**Cache reads of a compaction.** For each compaction whose result reports its token counts, a `compaction_cache` row records the prefix read, the share of the cached prefix that the summary request read rather than wrote, and the uncovered input, the tokens outside the cache. Claude Code's compaction request places its one cache marker on the last summarized reply, so the context after it (for example a large batch of tool results) is uncovered input whether the cache is warm or cold, and it never makes a compaction count as cold. A main compaction of 100,000 tokens or more with a prefix read under 0.5 is cold: one `compaction_cold` row and alert A-28, a sign that the cache had expired or the request went to another model than the session's.

**Cache reads after a pause.** At the end of a turn, the watcher reads the main transcript's responses. The first response after a pause of 5 minutes or more gets one `cache_after_gap` row: the pause, the response's time, its cached reads, cache writes and uncached input, and `hit`, `miss` or `none`. A response is a `hit` when at least half of its cached prefix was read rather than written, and `none` when it had no cache tokens. The row also has Claude Code's cache miss reason, from the response's `diagnostics` in the transcript: a reason such as `previous_message_not_found` or `messages_changed`, `none` when Claude Code gave no reason, or `not-reported` when the response has no diagnostics. With a reason, it also has the missed token count that Claude Code gives. An unknown reason is logged as `other`. The row holds no text. The report pairs these rows with the keep-warm gaps before them (see [Keeping the cache warm](keep-warm.md#in-a-report)).

**Retention.** The folder grows with use and is never pruned automatically; no hook calls prune. Prune is built and off. Running `! "<plugin folder>/scripts/{{plugin}}-store" watch prune --days 30` in a session removes a session's watcher files, but only when every file of that session is older than 30 days. A session here means `<session>.jsonl`, `<session>.classic.jsonl`, `<session>.alerts.jsonl` and the whole `<session>/` folder, including `jobs.jsonl`, `jobs-pending.jsonl`, `queue-adds.jsonl`, `handoff-turn/`, `pending/` (kept mismatches too), `checkpoint/`, `dispatch/`, `bg/` and `offsets/`. One newer file, or a symlink anywhere in it, keeps the whole session. Prune never touches the shared files (`queue-caps.json`, `evidence-index.tsv`, `heal/`, `version.json`, `.orphans/`, `notice/`, `export-salt`, `install-id`, `reports/` and similar), the summary copies, the handoffs or the evidence.

**Time at the end of a turn.** The Stop hook gives itself 3.5 seconds, under half of its 8-second timeout, counted from the moment its helper starts (the launcher's own start comes before that). On a busy machine it first writes what the turn needs, then reads the logs on for as long as that time allows, and leaves the rest for the next turn; a late summary copy whose evidence there is no time left to copy waits for the next turn too, so its evidence is still copied. Its missing-copy alert (A-01) waits with it until a later turn, or the session's end, saves the copy (then no alert) or cannot (then the alert is raised); an A-01 whose copy is saved later is closed with an `alert_closed` row, reason `resolved: copy saved`. The watcher writes a `sweep_partial` row when it stops early. Each turn's end also writes a `stop_timing` row to `<session>.classic.jsonl` with how long the hook took and which steps it cut short (not with `watcher: false`). The folder size behind the `watch_quota_mb` warning (A-24) is measured at most once an hour per session, so the warning can come up to an hour after the folder grows past it; a measurement that runs long gives up and is tried at the next turn. A folder with more than 20,000 entries raises the warning too (the size it names is then a lower bound). Once the folder is back under the limit, the next measurement closes the warning with the reason `resolved: below quota`; a later rise on another day raises it again. The session's end gives its final save step only the time left of its own 5-second timeout, so a session that ends on a busy machine leaves a late copy for the next session to save, as a late turn's end does.

**Turning it off.** `watcher: false` stops new watcher rows, including the permission-denial and stop-failure rows. Logs already written are kept: nothing is deleted. The records that the copies, resume and status need are still written (copy checks, the background list, restart counters, rollups and liveness), and the first line of `/{{plugin}}:status` says so: `watcher: false · existing logs kept (nothing deleted) · core files still written: …`.

## Sending a report

`/{{plugin}}:report` bundles the watcher's content-free rows into one zip on your disk and prints its path. You send the file yourself, for example as an attachment to a message; the plugin uploads nothing. The skill first runs a dry run, which writes nothing, then the report itself, and reads no log itself. The same command works without the model: `! "<plugin folder>/scripts/{{plugin}}-store" report`, which `/{{plugin}}:status` prints with the real folder.

- **Inside:** `README.txt` (what is in the zip and how to look inside), `manifest.json` (plugin and Claude Code versions, operating system, helper runtime, the time window, file hashes, and what was withheld or dropped), `config.json` (your effective settings: numbers and on/off values as they are, paths only as `default`, `custom` or `unset`, pattern lists only as a count), `probes.json` (capability facts the plugin already recorded; the report runs no probe), `sizes.json` (folder sizes and file counts, no names) and `rows/`, one file per session. It also holds `keep-warm.json`, the keep-warm statistics built from those rows (see [Keeping the cache warm](keep-warm.md#in-a-report)). Timestamps are included as they are. A row names a handoff section by its fixed id, such as `main:next-steps` (the manifest's `spec_version` 2), never by its position.
- **Never inside:** conversation text, summaries and handoffs (unless you add them, below), commands, file paths, repository and branch names, settings paths.
- **Summaries and handoffs, only when you say yes.** When saved compaction copies or handoffs the plugin published exist in the report's time window, the skill asks once per report, one question for each of the two, whether to add them; each needs its own yes, no answer means no, and no setting adds them. With a yes, each copy goes under `summaries/` and each handoff under `handoffs/` with a hashed name, after the same two scans as the rows; any file with a hit is left out and listed as `WITHHELD`. The output lists each added file. Summaries and handoffs hold your sessions' text: your names, paths, hosts and secrets are scanned for, but business content is not masked. The manifest says `with_summaries` and `with_handoffs`, and `report verify` fails a zip whose summaries or handoffs the manifest does not declare. <!-- summaries and handoffs are each opt-in, with a separate yes -->
- **How it stays content-free.** Rows go through an allowlist per event and field; anything not on it is dropped and counted. Session, agent and task ids and repository and bucket names become salted hashes, and paths become their kind. Then each file is searched for your home folder, account name, host name, accepted repositories, repository and bucket folder names and git remote hosts, and scanned for secrets. A file with any hit is withheld and listed as `WITHHELD <file> (<reason>)`; the strings searched for are written nowhere.
- **Where.** `~/Downloads` when it exists, is writable and is outside a git work tree, else `<log_dir>/reports/`. The file is private (0600). The output ends with a `REVEAL` line (show the file in the Finder) and a `COPY` line (put the file on the clipboard, on macOS). They are shown for you to run; the skill does not run them, because the copy line replaces your clipboard.
- **Options.** `--since 7d` or `--since <YYYY-MM-DD>`; `--out <folder>`; `--max-mb N` (default 20; over it the newest rows are kept and the manifest says so); `--dry-run` lists what would go in, with `summaries: <n> available (<size>)` and `handoffs: <n> available (<size>)`, and writes no file; `--with-summaries` adds the summaries and `--with-handoffs` the handoffs (the skill passes each only after your yes to it). `report verify --zip <file>` checks a bundle's hashes, names and scans.

Making a report deletes nothing and leaves the existing logs as they are.

## Reporting problems

Open an issue at https://github.com/{{repo}}/issues with what you saw and the plugin version (`/{{plugin}}:status` shows it); attach a report zip only if you want to share the logs.

## A local comparison trial (off by default)

A development aid for comparing handoff instructions; you do not need it to use the plugin. It is off unless the file `~/.cache/{{plugin}}-trial/trial.json` exists and turns it on, and there is no setting for it in `/config`; without the file the plugin only checks, at each turn end, that it is still absent. The file names two instruction texts of your own with their sha256 sums (the plugin ships neither).

While it is on, at each handoff (and at each compaction when the file says so) the plugin asks Claude Code for up to two extra replies over the same conversation, one to each text, through the session's own client and credentials, so they use the session's allowance; a call whose instruction text is missing locally is not made. Each call sends the conversation, the last reply and git and handoff facts (branch, HEAD, recent log and diff stat, a project note file, `.remember/now.md`, when the repository has one, the queue list, the previous handoff in the same bucket in full). The calls do not show in the chat, no turn waits for them, and every tool is denied to them; the plugin's own handoff turn may start up to 3 seconds later. The replies are secret-scanned and redacted, then saved under `~/.cache/{{plugin}}-trial/` (files 0600) with a content-free record per moment. A record holds ids, times, hashes, sizes, statuses, token counts, the model and Claude Code version, the worktree path, branch, HEAD and dirty count, the repository and ticket bucket names, and the paths of the two saved replies, never their text; nothing is written under the handoff root, and nothing leaves your machine except those calls. A moment is skipped when a usage window is at 90% or more or unknown, when the prompt cache would be cold, or when the file's version, repository or folder pins do not match.

To turn it off, delete the file or set `"on": false` in it; the change takes effect from the end of the current turn. The trial also ends by itself after its `trial_until` date.
